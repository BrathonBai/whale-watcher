# 迭代 2026-11-03：摸摸头交互 + 动画性能

> 两件事一起做：① 旋钮在"没唤出菜单"时的滚动改成 **摸摸头**（随机互动动画）；
> ② 修动画卡顿/内存——根因不是 GIF 本身，是固件层的**帧节奏/降帧策略/换动作整屏刷新/逐段解码缓冲**。
>
> 状态：已编译、已刷机、设备在线（`hub_v2`，WiFi 正常）。旋钮手势需要上手转一下验证。

## 1. 交互设定（已实现）

### 1.1 摸摸头

- **触发条件**：菜单关闭、待机（`kIdle`）、不在录音/上行/放系统语音/说话态。
- **手势**（`app_ui.cc`）：
  - 来回搓：方向反转 ≥1 次且累计 ≥2 格（两格间隔 >0.9s 就重算，避免误触）；
  - 或连续单向 ≥8 格（快速搓）；
  - 反应冷却 2.2s（连续搓会每隔 2.2s 再随机一段，不会每格触发）。
- **反应**：从 `happy / tickle / shy / wave` 里随机（避免连续同一条），随机时长 **2.4–3.6s**，
  随机台词（`嘿嘿 / 好舒服 / 再摸摸 / 唔…痒 / 最喜欢啦`），LED 绿、表情 Happy；
  到点自动回待机并清掉"这轮反应自己的字幕"（不会误删随后到来的对话）。
- **日志**：`ui2: 摸摸头 #3：clip=4 3120ms（4 段可选）`。

### 1.2 音量移到菜单（旋钮让位后必须补）

- 长按按键 → 菜单 → 选「音量」→ 进入**音量模式**（不再直接退出）：
  旋转 ±5%/格、按键确认、长按取消、8s 无操作自动退出；字幕显示当前值。
- 菜单其余项（配网/电量/关机）、单击录音、长按开菜单的语义都没变。

## 2. 动画为什么卡：四个根因 + 修法（全部已改）

| # | 根因 | 修法 | 实测 |
|---|---|---|---|
| 1 | 上一轮"说话降帧"把 Speak/Happy 的帧周期压到 200ms（5fps）——互动动画正是 Happy，直接掉一半帧 | **删掉 mood 降帧**，动画一律按素材 fps（100ms@10fps）播；音频任务优先级 7 本来就会抢占 UI(4)，不需要降帧让 CPU | `fps=9` → **`fps=10~11`**（串口 1s 统计） |
| 2 | `画完再等 period` 被 20ms tick 量化，实测只有 9fps | **截止时刻累积**（`s_pet_due += period`，落后才重对齐）+ UI tick 20ms→**10ms** | 帧间隔稳定 ~100ms |
| 3 | 每次换动作（互动每次触发都换）都 `s_full_dirty` → **整屏 412×412 刷一次**，顶一下 | 换动作时先把**旧角色框从背景副本恢复**，本帧只刷"旧框 ∪ 新框"；`PlayClip` 不再置全屏脏 | 切换不再整屏刷 |
| 4 | 每段 clip 各占一份解码缓冲（6 段 ≈84 KB PSRAM，且碎） | 改为**全模块共享一份**（按最大段 14.1 KB 分配；同一时刻只有一段在播） | `共享解码缓冲 14.1 KB`（原 ~84 KB） |

## 3. 资产侧：121 帧太长，按实际使用裁短

互动只播 2.4–3.6s，但素材是 121 帧 @10fps（12.1s）——后 8 秒永远用不到，白占 flash/解码。

- 新增工具 **[`tools/pclp_trim.py`](../tools/pclp_trim.py)**：读 PCLP → 解出帧 → 保留前 N 帧 → 按原格式重编码，
  可选 `--verify` 逐帧回读比对（**已对 3 个文件验证通过**）。
- 已裁剪：`happy 121→48`、`tickle 121→48`、`shy 81→48`（shy 8fps → 6.0s，仍覆盖最长 3.6s 反应）。

```powershell
# 从归档里的完整版重新生成当前裁剪版（可复现）：
python tools/pclp_trim.py --in _archive\firmware-v1-2026-11-02\device\main\pet_happy.bin  --out firmware-v2\main\pet_happy.bin  --frames 48 --verify
python tools/pclp_trim.py --in _archive\firmware-v1-2026-11-02\device\main\pet_tickle.bin --out firmware-v2\main\pet_tickle.bin --frames 48 --verify
python tools/pclp_trim.py --in _archive\firmware-v1-2026-11-02\device\main\pet_shy.bin    --out firmware-v2\main\pet_shy.bin    --frames 48 --verify
```

| 指标 | 裁剪前 | 裁剪后 |
|---|---|---|
| 3 段互动 clip | 3.21 MB（121/121/81 帧） | **1.55 MB（48 帧 ×3）** |
| 固件 bin | 8,312,592 B | **6,495,216 B**（省 1.82 MB） |
| app 分区余量 | 34% | **48%** |
| 帧循环时长 | 12.1s | 4.8s（h/t）、6.0s（shy） |

> 43 行脚本的格式细节（一个关键坑）：PCLP 的 `flags` 是**整帧一个**，一帧里不能混用
> memset 和 XOR 两种指令；工具统一用 XOR（delta=0 即"跳过不改"），所以能正确复现任意帧间变化。

### 如果要用"大肥鱼 GIF 库"里的新动画

设备**不直接播 GIF**（GIF = LZW + 逐帧全图合成，在 S3 上必然卡）；现在是离线转 PCLP（4bpp 调色板 + RLE + 帧间 delta）。
建议转换参数（针对本屏/本内存预算）：

- 画布 **160×180**（角色区），居中、索引 0 透明；
- **8–10 fps**，单段 **≤72 帧**（互动 48–72 帧足够；待机循环可 96 帧）；
- 16 色调色板（深色背景 + 角色主色，避免渐变抖动）；
- 目标体积 0.4–0.6 MB/段（当前 48 帧 ≈0.4–0.68 MB）。

目前工作区没有 GIF 源文件（只有 design/ 里的预览 GIF）。如果要把"大肥鱼"库转成设备可播的 clip，
把 GIF 目录丢进工作区（或告诉我路径），我可以补一个 `tools/gif2pclp.py` 批量转换并直接出 6–9 段素材。

## 4. 顺带修的桥侧 bug（Opus 不该被待机 pong 误杀）

`/api/diag.audio` 显示：Opus 曾生效，随后被自适应降回 PCM，理由是"缓冲平均 0 ms → 差"。
根因：**待机时没有音频，pong 的 `bufMs` 必然是 0**，旧逻辑把它判 poor，连续两段就永久回退。
已改 `bridge/lib/audio_profile.js`：`bufMs==0 且无新增欠载` → **unknown（保持当前档位）**；
真欠载（同一窗口 underruns 增加）仍判 poor。`opus.test` 增 1 例（27 例全绿），已部署到运行态。
**注意：桥要重启 DSH 后才加载新代码**；重启后 `/api/diag.audio` 的 reason 会变成"待机 pong → 暂不降档"。
