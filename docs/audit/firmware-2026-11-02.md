## 1. 结论摘要

1. **语音播放链路有一条"用错长度的尾垫"**：`s_pad` 只申请 120 ms（2880 采样 / 5760 B），收尾时却按 180 ms（4320 采样 / 8640 B）
   读它 → **每次 `audio_end` 都越界读 2880 B PSRAM 当音频播**（FW-01）。这是本轮最直接、每天都会执行的确定缺陷。
2. **摄像头"按需拍照"的实现有内存破坏风险**：JPEG 缓冲只在第一帧按当时长度分配，之后帧更大时 `memcpy`/base64 解码**越界写**；
   且 `Shoot()` 在 **WS 收包任务里 `vTaskDelay(1500)`**，播报中拍照会把 32 KB 收缓冲灌爆 → `rx overflow` 断连（FW-02/FW-03）。
3. **状态机只有"开始"，没有"结束/超时"闭环**：清字幕不重绘 → 旧字幕永久停留（FW-06）；`say` 之后没有音频时 LED/表情永久停
   （FW-09）；非流式 TTS 每句一个 `audio` 头把 `mp3` 暂停深度泄漏（FW-07）；10 s 语音上行在 UI 任务里同步发送，按实测链路要
   **8–23 s 才发完**，期间按键与超时全部停摆（FW-04）。
4. **协议边界和契约不一致**：`ws` 层把 **>512 B 的下行文本整帧丢弃**，而桥默认 `maxReplyChars=240`（≈720 B UTF-8），
   长回复会"没字幕、没表情"（FW-05）；`audio`/`audio_end` 的 `seq` **完全不校验**，契约 §2 写的"对账丢帧"没有实现（FW-08）。
5. **恢复与可观测性偏弱**：`nvs_flash_init()` 返回值、`audio::Init()` 结果、摄像头失败、PSRAM 失败多处静默或只有一行日志；
   WiFi 断线处理在**默认事件循环任务里 `vTaskDelay(1000)`**（FW-10/FW-11/FW-18）。

**严重度计数**：P0 = 0，P1 = 5，P2 = 9，P3 = 13（共 27 条；逐条见 §2）。

### 2.2 逐条证据

#### FW-01 P1 · 尾垫越界读（每次 `audio_end` 必现）
**证据**
- `app_ui.cc:49-51`
  ```cpp
  constexpr int kPadHead = 24000 * 120 / 1000;   // 120 ms = 2880 采样
  constexpr int kPadTail = 24000 * 180 / 1000;   // 180 ms = 4320 采样
  int16_t* s_pad = nullptr;
  ```
- `app_ui.cc:369`（只按头垫大小申请，`calloc` 只清零 5760 B）
  ```cpp
  s_pad = (int16_t*)heap_caps_calloc(1, (size_t)kPadHead * 2, MALLOC_CAP_SPIRAM);
  ```
- `app_ui.cc:279` / `app_ui.cc:284`
  ```cpp
  if (s_pad) audio::StreamWrite(s_pad, kPadHead);   // 2880 采样：在界内
  ...
  if (s_pad) audio::StreamWrite(s_pad, kPadTail);   // 4320 采样：越界 1440 采样 / 2880 B
  ```
**推理链**：`StreamWrite` 逐采样 `s_ring[s_head] = buf[i]`（audio.cc:106-112），不检查 `buf` 边界。尾垫调用读 8640 B，
但分配只有 5760 B → 越过分配末尾 2880 B 读 PSRAM 堆（内容不可控，大概率不是 0）。
**影响**：① 每段 TTS 结尾实际播放的是"120 ms 静音 + 60 ms 堆内存当 PCM"，听感是收尾"咔/噪声"；
② 越界读本身不写内存，但读数取决于堆布局，若分配正好位于 PSRAM 堆尾部则可能读到未映射页（待验证，见下）。
**修复**：`s_pad` 按 `kPadTail` 申请（`kPadTail * 2`），或分别申请两块；顺手加 `if (!s_pad) ESP_LOGE(...)`。
**待验证**：串口在每段 TTS 收尾时听/录尾音；或临时把 `kPadTail` 改成 `kPadHead` 对比尾音（不能在本阶段做）。

#### FW-02 P1 · 摄像头 JPEG 缓冲只按首帧分配 → 后续帧越界写
**证据**：`camera.cc:76-85`（base64 JSON 路径）
```cpp
if (!s_jpeg) s_jpeg = (uint8_t*)heap_caps_malloc(blen, MALLOC_CAP_SPIRAM);  // ← 只在第一帧分配
if (s_jpeg) {
    s_jpeg_len = B64Decode(b, blen, s_jpeg, blen);   // out_cap 用的是"本帧" blen，不是分配到的容量
```
`camera.cc:98-105`（裸 JPEG 事件路径）
```cpp
s_jpeg_len = (int)r->len;
if (!s_jpeg) s_jpeg = (uint8_t*)heap_caps_malloc((size_t)r->len, MALLOC_CAP_SPIRAM);  // ← 同样只分配一次
if (s_jpeg && (size_t)s_jpeg_len <= r->len) {          // s_jpeg_len == r->len，条件恒真
    std::memcpy(s_jpeg, r->data, r->len);              // 更大帧 → 写越界
}
```
**推理链**
- 裸 JPEG 路径：分配容量 = 第一帧 `r->len`；第二帧更大即 `memcpy` 溢出（无任何 1.33 余量），**任何尺寸增长都触发**。
- base64 路径：分配容量 = 第一帧 base64 字符数 ≈ 1.33×JPEG₁；解码后需要 JPEG₂ 字节 → 溢出条件 ≈ `JPEG₂ > 1.33×JPEG₁`，
  即画面细节/亮度变化使 JPEG 体积涨 33% 以上（240×240 JPEG 5–6 KB，涨到 7–8 KB 很常见）。
**影响**：PSRAM 堆被写坏 → 随机崩溃/重启、或后续分配内容被污染；`s_jpeg` 是持久缓冲，一旦破坏会持续恶化。
**修复**：记录 `s_jpeg_cap`，每帧 `if (blen > s_jpeg_cap) { free; malloc(blen); s_jpeg_cap = blen; }`；`heap_caps_malloc` 失败要打日志并跳过上报。
**待验证**：串口看事件是 `事件 N 字节（JPEG！）`（裸 JPEG 路径，则几乎必现）还是 `JPEG 解码 N 字节（base64 M）`（base64 路径）；
再连续拍 10 张看 `base64` 长度是否波动 >33%。

#### FW-03 P1 · `camera::Shoot()` 在 WS 收包任务里阻塞 1500 ms
**证据**：`app_ui.cc:263`（下行文本回调，运行在 `ws` 任务上下文）
```cpp
if (std::strstr(buf, "\"shot\"")) { camera::Shoot(); ESP_LOGW(TAG, "下行要求拍照"); return; }
```
`camera.cc:146-152`
```cpp
void Shoot() {
    if (!s_client || s_busy) return;
    s_busy = true;
    sscma_client_sample(s_client, 1);
    vTaskDelay(pdMS_TO_TICKS(1500));   // 等事件回来
    s_busy = false;
}
```
**推理链**：`ws::SessionOnce` 的收包循环（ws_client.cc:212-314）与文本回调在**同一个任务**；这 1.5 s 内不 `recv`。
TTS 下行是连续 4 KB 二进制帧、48 KB/s（契约 §1 音频格式），32 KB 读缓冲约 **0.68 s 就填满**；缓冲满且解析不出完整帧时
`have == kReadBuf` 分支判 `rx overflow` 并断连（ws_client.cc:302-309）→ 设备重连、语音中断。
**影响**：播报中调用 `device_shot`（桥 `device_shot` 工具/`POST /shot`）⇒ 音频被打断甚至断连；若正在上传语音，同样会中断。
**修复**：`Shoot()` 改成只投递请求（置 flag/队列），由独立任务或用 `sscma_client` 的异步回调 + 超时完成；WS 回调里不得 `vTaskDelay`。

#### FW-04 P1 · 语音上行在 UI 状态机任务里同步发送 → 最长 8–23 s 阻塞
**证据**：`app_ui.cc:136-167`（`TickTask`，优先级 3、周期 30 ms 的状态机）
```cpp
const size_t bytes = (size_t)s_got * 2;              // 10 s 上限 = 480,000 B
char h[160];
const size_t hn = proto::BuildVoice(h, sizeof(h), (int)bytes, ++s_seq);
bool ok = ws::SendText(h, hn);
const uint8_t* p = (const uint8_t*)s_buf;
size_t off = 0;
while (ok && off < bytes) {
    const size_t n = (bytes - off) > 16384 ? 16384 : (bytes - off);
    ok = ws::SendBinary(p + off, n);                 // 每次内部 SendAll 阻塞、SO_SNDTIMEO=5 s
    off += n;
}
...
s_got = 0;
s_state = kIdle;                                     // ← 发完才回 idle
```
`ws_client.cc:92-111`（`SendAll` 循环 `send()`，超时才返回）、`ws_client.cc:348-365`（`SendBinary` 持 `s_tx_mutex` 最长 3000 ms）。
**推理链**：`SendBinary` 在 TCP 发送窗口（32 KB）填满后阻塞，直到对端 ACK。按 TODO §0 基线，链路 21–59 KB/s；480 KB ⇒
**8–23 s** 才发得完。这期间 `TickTask` 不处理菜单/字幕超时/`hello`，且 `s_state` 仍是 `kSend`，`OnClick` 只认 `kIdle/kRec`
（app_ui.cc:190-204）⇒ 用户按单击无任何反应（看起来像"死机"）。
**影响**：每次长录音（>3 s）后设备"卡住"若干秒；`ws` 任务同时可能因 `s_tx_mutex` 被占用最长 3 s 而无法回 pong。
**修复**：语音上行移到独立低优先级任务（或 `ws` 任务内做非阻塞发送队列），UI 状态机只投递"待上传"事件；`SendBinary` 用短超时 + 失败计数。

#### FW-05 P1 · 下行文本 >512 B 整帧丢弃，与桥的 `say` 长度上限冲突
**证据**：`ws_client.cc:201-209`
```cpp
void OnFrameText(const uint8_t* data, size_t len) {
    ++s_stats.rx_frames;
    // 超长文本帧直接丢：桥的 welcome 有 1520 字节，下游缓冲撑不住（实测 Cache error 重启）
    if (len > 512) {
        ESP_LOGW(TAG, "丢弃超长文本帧 %u 字节", (unsigned)len);
        return;
    }
```
桥侧：`bridge/lib/protocol.js:176` `say()` 截到 **2000 字符**；`bridge/lib/config.js:33` 默认 `maxReplyChars: 240`；
`bridge/lib/index.js:69` 的 `clampReply` 按该值截断。**240 个汉字 ≈ 720 B UTF-8 + JSON 头 ≈ 755 B > 512 B**。
**推理链**：桥按契约发 `say`，固件在传输层整帧丢弃，`proto::Parse` 根本没被调用 ⇒ `ShowText`/`SetMood`/`led::Set(kSpeak)` 全不执行。
更糟的是**没有回执/错误帧**，桥侧 `device.say()` 返回 `sent:true`，日志一切正常 ⇒ "字幕消失"表现为偶发、不可诊断。
**影响**：默认配置下，回复超过约 **158 个汉字**（含 JSON 头 512 B 上限）就完全无字幕、无表情；只有音频照播。
**修复**：三选一并对齐：① 固件 `OnFrameText` 上限提到 ≥ 8 KB（`buf` 是静态 560 B，需同步放大到 8 KB 或改流式解析）；

所以 hello 之前不会有服务端数据，**暂不触发**；但桥侧任何"onOpen 立即发帧"的改动都会让固件进入该状态。
**修复**：把 101 之后剩余的 `got - (header_end)` 字节 `memmove` 进 `SessionOnce` 的收缓冲（或让 Handshake 接收/返回剩余字节）。
**待验证**：断线日志里是否出现"连上后立刻 frame error"；用 `tcpdump`/桥日志看 101 与 welcome 是否同段。

#### FW-21 P3 · 重连退避无 jitter；UDP 发现无认证
**证据**

**修复**：发现报文加共享 token/版本校验；退避加 ±20% jitter。

#### FW-26 P3 · 折行兜底可能切在多字节中间；B64 非法字符静默
**证据**
- `text_draw.cc:244-251`：

- `camera.cc:29-31`：`if (d < 0) continue;` 对非 base64 字符跳过而非报错；坏数据仍会被解出并上报（见 FW-18 的魔数检查不阻断）。
**修复**：`le` 回退到最近的 UTF-8 起始字节；B64 非法字符计数超阈值直接丢弃该帧。

#### FW-27 P3 · 渲染初始化失败只一行日志后继续（黑屏无重试）
**证据**：`app_main.cc:57-66`
```cpp
if (watcher::LcdInit(&panel) == ESP_OK) {
    watcher::BacklightInit();
    if (!render::Init(panel)) ESP_LOGE(TAG, "render init 失败");   // ← 继续往下跑
    clip_player::Init();
    ...
} else {
    ESP_LOGE(TAG, "面板起不来");
}
```
`render::Init` 需要三块内存：整帧 340 KB（PSRAM）、整帧背景副本 340 KB（PSRAM）、**DMA 条 412×24×2 = 19,776 B（内部 RAM，`MALLOC_CAP_DMA|INTERNAL`）**（render.cc:406-426）。
任一失败 → `render::Init` 返回 false → `render::Ready()` 为 false → `Tick()` 直接 return（render.cc:484）⇒ **屏幕永久黑/停在开机背光**，
之后只有 `SetText/SetMood` 改内存变量，无任何告警或重试。
**影响**：内部 DMA 内存碎片化时（历史串口日志出现过"内部 20439 B / 最大块 8192 B"），这块 19.7 KB 连续分配是最脆弱的一环；
失败后设备"活着但黑屏"，日志只有一行。
**修复**：失败时把 `s_strip_rows` 降到 8/4 重试；仍失败则点亮屏上错误/周期性重启，而不是静默黑屏。
