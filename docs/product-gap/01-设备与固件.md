## 1. 结论摘要（10 行）

1. **这不是一台「能卖」的设备，是一台「能演」的设备**：语音闭环、412 圆屏动画、旋钮/触摸互动、Opus 下行、WiFi 稳定性与可观测性都达到了「原型可用且不丢人」的水准；但**配网、OTA、设备身份、电源策略、量产安全**五件事基本是空的。
2. **最硬的三块 P0**：① **没有任何运行时配网通道**（换网=改 `wifi_local.h` 重编重刷，菜单「配网」项直接提示重刷）；② **没有任何 OTA 通道与可用回滚**（固件无 `app_update`/`esp_https_ota`，`otadata` 无效、实际单槽 ota_0 在跑、`CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE` 未开）；③ **设备身份与链路安全缺失**（hello 无唯一 ID；WS 只支持 `ws://`、握手无鉴权；UDP 发现无认证，可被同网段冒充桥窃听麦克风/图像或冒充设备向 LLM 注入内容）。
3. **第 4 块 P0 是供电**：400mAh ≈ 1 小时、必须插电；固件无电量/充电上报（`state` 明确不支持）、无低电策略；菜单「关机」= 直接切断 `PWR_SYSTEM` 的**硬断电且无唤醒路径**。
4. **第 5 块 P0 是量产安全**：`CONFIG_SECURE_BOOT`/`FLASH_ENCRYPTION_ENABLED` 均未开，WiFi 明文存 NVS、且 `wifi_local.h` 会编进固件二进制（模板自己都写了「固件二进制里能看到」）——这两项 eFuse 是**一次性**的，必须在首批投产前决策，事后无法补。
5. **当前 capabilities 的「不支持」不是小事**：`press/record/mic/state/level/sound/diag/text` 八项不做，等于**大脑对设备几乎全盲**（不知道电量、不知道按键、不能主动听、不能远程诊断），产品化的「主动陪伴 / 售后运维 / 低电提醒」都建不起来；好消息是 `proto.cc:347-447` 已写好其中 5 个编码器，接线成本低（见 §5 第 3 条）。
6. **可靠性有仪表盘但没闭环**：复位原因、栈水位、coredump 配置、pong 自诊断都做了（值得保留）；但任务看门狗不触发重启、无长跑/温升/重连率数据、无远程遥测——现场出问题只能拔下来插 USB。
7. **交互已过「能玩」线但没过「能懂」线**：触摸 + 旋钮 + 按键三套输入都有，但**录音的唯一入口是旋钮按键**（触摸没有「说话」），菜单只是字幕里的一行 `> 音量`（渲染层 `render::SetMenu` 已实现却没人调用），没有常驻在线/电量状态。
8. **感知是「按需快门」，不是「陪伴之眼」**：Himax NPU 与摄像头在位，但 v2 只接受 `shot` 拍一张（240×240 JPEG），人检测未接入、拍照无任何指示灯/遮挡、相机无电源控制（常供电）。
9. **「已具备，别重做」的比想象中多**：协议 v2 契约与能力协商、Opus 全链路与显式回退、音频环缓/优先级、6 段内嵌动画、旋钮正交解码、触摸手势状态机、WiFi 凭据多来源/PS 关闭/BSSID 锁、WS 帧层、复位原因/栈水位/coredump 分区、TF 卡非致命挂载、桥侧 10+ 套回归——这些已经是产品级或接近产品级。
10. **建议的推进顺序**：先做「可出厂」三件（配网+身份、OTA/回滚、链路认证）与「电源形态」决策，再补「首版体验」四件（唤醒/打断、状态上报、隐私指示、菜单/说话入口），制造与安全 eFuse 在首批投产前完成；**不要先做动画/表情/音色**，那是 P3。

## 4. 缺口表（按 10 个维度）

> 读法：每条缺口 = **ID / 严重度 / 证据 / 为什么阻碍产品化 / 验收判据**。
> 严重度定义：**P0** 不解决不能量产（配网/OTA/安全/供电/身份这类）；**P1** 首版必须；**P2** 后续版本；**P3** 优化。
> 与既有审计的关系：`docs/audit/firmware-2026-11-02.md` 是**代码缺陷**审计（FW-01…FW-27，P0=0/P1=5）；本篇是**产品化差距**审计，不重复缺陷条目，只在交集处引用 FW 编号。

### 4.1 维度 1：启动 / 身份

**结论**：启动链本身是健康的（复位原因、版本、内存、分级初始化、失败不 abort），但「出厂态」几乎是空的：没有首次开机引导、没有唯一身份、没有恢复出厂；无 Wi-Fi 凭据时设备**静默停在待机屏**，用户侧得不到任何信息。

| ID | 严重度 | 证据（file:line / 文档 / 日志） | 为什么阻碍产品化 | 验收判据 |

#### P0 展开：G1-02 设备身份

- **现状**：设备对桥而言是「一个连接」，不是「一台设备」。`hello` 里的 `ver="0.2"` 是**固件版本**而非设备版本；`board="watcher"` 是型号。没有任何字段能区分两台同型号设备。
- **为什么是 P0**：OTA 灰度、绑定、防克隆、售后定位、多设备共存、用户换机，全部以「唯一 ID」为主键。等到 OTA 上线再补 ID，会让历史设备无法迁移（要么全部算「未知设备」）。
- **建议做法**：`esp_read_mac()` 取 STA MAC → 派生 SN（如 `JJ-<6字节hex>`）；若产线要可读 SN，用 eFuse 用户块或加密 NVS 烧录；`hello` 增 `devId/model/hw`；桥维护 device 表（devId → 会话/绑定/固件版本/最近遥测）。
- **依赖**：G10-02（产线烧录）与 G9-02（安全启动）会用到同一套身份体系，建议一次设计。

#### P0 展开：G3-01 / G3-02 OTA 与回滚

- **现状**：`ota_0`（0x200000）在跑 v2；`ota_1`（0xe00000）曾是 v1 的备份/或空；`otadata` 无效意味着 bootloader 每次都选 ota_0——**即使你把新固件写进 ota_1，设备也不会从它启动**，除非同时写 otadata。这是「槽在、机制没启用」的典型状态。
- **产品必须的机制**（按里程碑）：
  1. **M1（可回滚的 USB 升级）**：`idf.py` 产出的 ota 镜像 + 写 otadata 的脚本；刷完能 `esp_ota_get_running_partition()` 证明从 ota_1 启动；异常可一键回 ota_0。
  2. **M2（局域网 OTA）**：桥提供 `/firmware` 静态服务 + `esp_https_ota`（或自定义 HTTP 客户端，固件已有 `esp_http_client` 依赖）；下载到 ota_1、校验 SHA256/签名、`esp_ota_set_boot_partition`、重启。
  3. **M3（云 OTA + 灰度）**：设备上报 `devId/fw/ver`，服务端按批次下发；支持暂停/回滚/强制升级。
- **关键配置**（必须显式写进 `sdkconfig.defaults` 并进版本库，见 G10-04）：`CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE=y`、`CONFIG_PARTITION_TABLE_CUSTOM=y`（已有）、`CONFIG_APP_PROJECT_VER_FROM_CONFIG=y` 或 CMake 注入 git SHA、`CONFIG_SECURE_SIGNED_APPS_NO_SECURE_BOOT=y`（在还没上 Secure Boot 前先做签名校验）。
- **与 coredump 的关系**：回滚判据除了「起不来」，还应包含「起来后 30s 内没 mark valid」——这样即使 app 能启动但功能坏（比如音频线程崩），也能回滚。

  2. **带电池的桌面机（推荐过渡）**：400mAh 仅作优雅关机缓冲（10 分钟），主供电 5V；拔电后自动保存状态并关机，插电自动开机。
  3. **可移动版本**：换 ≥2000mAh 电池 + 充电管理 + 低电策略 + 休眠唤醒（成本最高，需要重新做外壳与认证）。
- **无论哪种**，「关机」都必须可唤醒、低电必须可见、充电必须有指示——这三条是用户体验底线，不是可选项。
- **热设计**：屏幕 412×412 + 背光 80% + Wi-Fi 常开 + 相机常供电，是最热组合；建议先测 24h 表面温度再定背光曲线与是否给相机断电。

#### P1 展开：G5-01/G5-02 为什么是「首版必须」而不是「以后再说」

- 产品的核心叙事是「它会看着你、会先开口、会被叫到名字时抬眼看你」（`docs/伙伴形态-可行性.md:36,92`）。**唤醒词**是「叫名字」的物理实现；**AEC/VAD** 是「能插话」的物理实现。这两件不做，「陪伴」就退化成「按键问答玩具」。
- 硬件限制要提前写进规格，避免过度承诺：单麦无 AEC 是硬限制（`docs/伙伴形态-可行性.md:53`），要么外接麦克风/双麦，要么接受「按键打断」。**产品文案不能承诺「随时打断」**，除非先做 AEC 验证。
- 软路线（不改硬件）：先做「按键打断 + 录音中检测 TTS 是否在播则先停播」，成本低、体验立刻改善；再做 ESP-SR 的 AEC/VAD（需要模型/内存/授权，`docs/迭代-2026-11-03-固件配置与稳定性.md:419` 已列为另立项目）。

#### P0 展开：G9-01 链路安全的攻击面

- **设备 → 桥方向**：设备开机广播 `{"t":"who"}` 到 `255.255.255.255:7789`，任何同网段机器回一个 JSON（`{"port":...}`）就能被设备采纳为桥地址（`bridge_find.cc:51-69`，只取来源 IP，不校验内容）。此后设备的 `voice`（麦克风 PCM/Opus）与 `image`（摄像头 JPEG）都会发给它。**攻击成本 ≈ 20 行 Python。**
- **桥 → 设备方向**：桥的 WS 端点 `/device` 无鉴权（`bridge/ws.js` 无 token 校验；运行态 `panelToken` 为空），任何能连 7788 的客户端都能冒充设备发 `voice`/`image`。桥会把它送进 ASR→LLM→工具链（DSH 会话），等于**给局域网攻击者一个向 Agent 注入内容的入口**。
- **修复优先级**：① 设备-桥配对密钥（首次配网时下发，存加密 NVS）；② WS 握手带 token + TLS（或至少在局域网用 token + 消息签名，配合 G9-02 的 flash 加密保护密钥）；③ UDP 发现只用于「找地址」，找到后必须完成配对握手才能传输数据；④ 桥侧 `rejected` 计数与告警（现在 `rejected=0` 说明根本没拒绝过任何连接）。
- **注意**：这不是「以后上云再做」的事——即使只做局域网，语音/图像已经是个人敏感信息。

### 6.3 给 Lead 的三句话建议

1. **先冻结「不可逆决策」**：电源形态、Secure Boot/Flash 加密、身份规则、配网形态、OTA 通道——这五件一旦量产就改不动（或代价极高），必须 M0 拍板。
2. **P0 只做 4 件事**：配网、OTA+回滚、身份+链路认证、电源策略；这四件决定「能不能卖」，其余都是「好不好用」。
3. **别重做已具备的**：协议/Opus/音频环/渲染/输入/Wi-Fi/WS/可观测/桥回归都已成型；把工程资源压在缺口上，尤其是产测与运维（现在完全是 0）。
