# 平台选型复盘：ESP32-S3 还是树莓派 / 香橙派

> 2026-10-28。触发问题：「ESP32 性能实在有限，为什么不是树莓派或者香橙派？」
> 这份文档只回答一件事：**当前项目的负载，到底卡在哪一层；换平台能不能解决。**

---

## 0. 结论（先看三行）

1. **你的直觉对了一半**：如果目标是「端侧跑 ASR/LLM/视觉」，ESP32-S3 确实到顶了，而且树莓派 Zero 2 W 也到顶——那需要 Pi 5 / 香橙派 5 / Jetson 级。
2. **当前项目不是这种情况**：设计文档 §1–§3 写的是 L0/L1 在设备、L2 在云；在这个分工下，S3 的余量足够，慢的主因是**实现**（全块重算、单缓冲、预算口径算错 4 倍），不是芯片。
3. **换平台的真实成本不在软件**（`core/` 是纯 C++，已能在 MSVC 下编译），而在**机械件**：412×412 圆屏、外壳、电池、麦克风/喇叭、2.65° 装配公差全部重做。Watcher 是成品，Pi 方案要自己开模或退回模块堆叠。

## 1. 把「性能不够」拆成四个问题

| 负载 | 当前实测/预算 | S3 余量 | 换 Pi 是否有用 |
|---|---|---|---|
| 412×412 全屏刷新 | 纸面 98ms（10fps） | 见 §2：口径错了，实际带宽是 4 倍 | **没用**。LVGL 全屏刷在 Pi 上一样慢，除非上 DRM/GPU |
| 140×140 局部动画 | 19.6ms/帧（30fps 够） | 够；CPU 单帧 ~14ms，可压到 3–5ms | 有用但没必要 |
| 24kHz 单声道麦克风 + VAD | 48KB/s，DMA 回调只算能量 | 大量余量 | 没必要 |
| 端侧 ASR / LLM / 多路视觉 | 未实现 | **不够**（S3 无 MMU、512KB SRAM + 8MB PSRAM） | Zero 2 W 也不够；要 Pi 5 / Orin |

一句话：**前三项 S3 够，第四项换 Zero 2 W 也救不了。** 真正需要换平台的是第四项，而第四项在你的设计里本来就在云端。

---

## 2. 你感觉「慢」的三个真实原因（两个是实现，一个是口径）

### 2.1 预算表把显示带宽算低了 4 倍

[`firmware/main/core/dirty.h:52-54`](../firmware/main/core/dirty.h#L52-L54) 的换算：

```cpp
// 412×412 / RGB565 / SPI3 @40MHz ⇒ 5.0 MB/s
inline double budget_ms(int px) { return px * 2.0 / 5000.0 * 1.45; }
```

5.0 MB/s 是 **单线 SPI** 的带宽。Watcher 的屏是 **QSPI 4 线**（[`board_watcher.cc:119-141`](../firmware/device/main/board_watcher.cc#L119-L141)：`data0..3` + `quad_mode = true`），40MHz × 4bit / 8 = **20 MB/s**。

| 口径 | 全屏 339KB | 140×140 39KB |
|---|---|---|
| 5 MB/s（现用） | 98ms | 19.6ms |
| 20 MB/s（实际） | **24.6ms** | 4.9ms |

所以「整屏切换 98ms、只能 10fps」是**纸面假设**，不是硬件上限。真实瓶颈是下面两条。

### 2.2 每帧整块重算 + 单缓冲 + 等 DMA 完成

[`app_main.cc:230-257`](../firmware/device/main/app_main.cc#L230-L257)：每帧把 140×140 全部像素用浮点 `sin/cos/sqrt` 重算一遍（19,600 px），再 `LcdDrawBand` **阻塞等 DMA 完成**（[`board_watcher.cc:288-297`](../firmware/device/main/board_watcher.cc#L288-L297)，最长 2s）。没有双缓冲、没有脏矩形、没有 LUT。

这不是「S3 算不动」，是**每帧干了 20 倍的活**。同样代码搬到 Pi 上，如果还是全屏重算，一样掉帧。

### 2.3 两套实现 + 状态机卡死

上一轮审计已经实测：云端 `speaking/presence` 停发就永不释放、`ui_state` 通知栈 5 轮涨 5 层、device 固件根本不接 `core/`。**「看起来性能不够」有一部分是「它根本没在按设计跑」。**

## 3. 平台对照（只列和这个项目相关的维度）

| 维度 | ESP32-S3（Watcher/Cardputer） | Pi Zero 2 W | 香橙派 Zero 2W | Pi 5 / 香橙派 5 |
|---|---|---|---|---|
| 算力 | 2×LX7 @240MHz | 4×A53 @1GHz | 4×A53 @1.5GHz | 4×A76 @2.4GHz |
| 内存 | 512KB SRAM + 8MB PSRAM | 512MB | 1–4GB | 4–16GB |
| 冷启动到出画面 | **0.3–0.8s** | 15–25s（精简 6–10s） | 15–30s | 20–35s |
| 活跃功耗 | **0.3–0.6W** | 0.8–2.5W | 1–3W | 3–8W |
| 1750mAh 电池续航（含屏，估算） | **10–15h** | 3–4h | 2–4h | 1h 级 |
| 显示接口 | QSPI 直驱 412×412 | DSI/HDMI（需另配屏） | HDMI/DSI | HDMI/DSI |
| 音频 | I2S + 硬件 codec | I2S HAT / USB | I2S HAT / USB | 同左 |
| 硬实时 | **FreeRTOS，中断 µs 级** | Linux，GPIO 抖动 10µs–ms | 同左 | 同左 |
| 掉电可靠性 | 无文件系统，天然安全 | SD 卡易损，需只读根 + A/B | 同左 | 同左 |
| 端侧 whisper/llama | 不可行 | tiny 勉强，llama 不可行 | 同左 | **可行** |
| 体积/装配 | 成品整机 | 需自开模或模块堆叠 | 同左 | 更大 |
| 成本（含屏/音频/电源/外壳） | 成品 $69–99 | ¥350–600 + 工时 | ¥300–550 + 工时 | ¥800–1500 |

> 数字是典型值/量级，用于比较，不当作规格书。

## 4. 决策树（按「必须端侧跑什么」分）

```
必须在设备本地跑 LLM / VLM / 实时多路视觉？
├── 是 → Pi 5 / 香橙派 5 / Jetson Orin Nano（Zero 2 W 不够）
│        代价：体积、风扇、3–8W、启动 20s+、机械重做
└── 否 → 继续问：必须电池供电 + 口袋尺寸 + 上电即出表情？
    ├── 是 → ESP32-S3（当前方案）
    │        大脑放云或局域网 PC；设备只做躯干 + 反射弧
    └── 否 → Pi Zero 2 W 可行（插电桌面形态、Python 生态、快速迭代）
             代价：启动慢、SD 卡、实时性弱
```

**混合方案**（推荐给「想端侧智能但不想放弃口袋」）：
S3 做躯干（屏/麦/按键/反射弧），局域网里放一台 Pi Zero 2 W 或旧笔记本做**本地大脑**（whisper.cpp + 小模型 + 视觉），两者走 WebSocket。设备端一行不用改，只换 `prototypes/cloud/agent.py` 的部署位置。这是当前架构天然支持的。

## 5. 如果真换平台，迁移成本是多少

| 资产 | 能否复用 | 说明 |
|---|---|---|
| `firmware/main/core/`（event/event_bus/ui_state/dirty） | ✅ **原样复用** | 纯 C++，无 IDF 依赖；已用 MSVC 编译通过（现位于 `..\embodied-watcher\firmware\`，宿主单测 `firmware\host\build_tests.bat`） |
| `firmware/host/sim.cc` | ✅ 原样复用 | 宿主仿真 |
| `prototypes/cloud/`（agent.py）· `prototypes/embodied/`（gateway.py） | ✅ 原样复用 | 只换 IP |
| `..\embodied-watcher\proto\schema.json` | ✅ 原样复用 | 与平台无关（早期草稿，现以实现为准） |
| `boards/`（屏/音频/输入驱动） | ❌ 全部重写 | S3 的 `esp_lcd`/I2S 换成 Linux DRM/ALSA |
| 外壳 / 屏 / 电池 / 麦克风 | ❌ 重做 | 412×412 圆屏 + 2.65° 公差是 Watcher 独有的 |
| 分区/OTA/救砖体系 | ❌ 重做 | SD 卡 + A/B + 只读根 |

**结论：软件迁移约 1–2 周，机械与整机集成 1–2 个月。** 这就是为什么「换平台」在小项目里通常不是技术决策，而是产品决策。

## 6. 留在 S3，立刻能做的三件事（把「性能不够」证伪）

1. **双缓冲 + 脏矩形**：`LcdDrawBand` 改成两份 iris 缓冲轮换，等 vSync 而不是等 DMA；只重画与上一帧不同的条带。目标：140×140 从 19.6ms 降到 <8ms。
2. **渲染 LUT**：`RenderIris` 的 `sin/cos/sqrt` 每像素算一次 → 预计算 `r38/r25/r13` 的平方表和 `sin/cos` 表（按 0.5° 步长），内层循环只剩整数比较。目标：单帧渲染 14ms → 3–5ms。
3. **预算表改实测**：把 `budget_ms` 的 5000 改成实测带宽（先量 `esp_lcd` 实际 flush 吞吐），否则所有「够不够 30fps」的结论都偏保守 4 倍。

这三件做完还掉帧，才是真的到顶——那时再换平台，判断就有依据了。

---

## 7. 触发「必须换」的硬指标（达到任意一条再换）

- 设备端需要跑 **>100MB 参数**的模型，或需要 **>2 路** 摄像头同时处理；
- 需要 Linux 用户态工具链（OpenCV / ROS 2 / Python 包）直接跑在设备上；
- 交互延迟要求里，**云端往返 >150ms 不可接受**，且本地必须有 ASR/LLM；
- 需要多进程/多用户/容器隔离。

没达到这些之前，S3 + 云大脑是成本最低、形态最好的组合；达到之后，Zero 2 W 也不是答案，直接上 Pi 5 / Orin。
