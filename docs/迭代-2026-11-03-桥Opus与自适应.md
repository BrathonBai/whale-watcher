## 一、为什么做 & 结论

PCM 24k/16bit/mono 是 48 KB/s，一段 6 s 语音 ≈ 288 KB，局域网拥挤/BLE 掉速时容易把设备音频环形缓冲抽干
（表现为"卡顿→watchdog 复位→掉线"）。Opus 在 16 kbps 下传同样内容只需 ≈ 2 KB/s，且能按链路健康度在
8/16/24 kbps 之间切档，因此本轮把"桥合成 PCM → 设备写 I2S"扩展成"桥合成 + 可选 Opus 编码 → 设备解码播放"。

三条设计底线（沿用本仓库的审计文化）：

1. **失败绝不静默**：编码不可用/失败 → 本段**显式**回退 PCM，且原因写进 `/api/state.audio.lastEncodeError`
   与 `/api/diag.audio`；日志同步 warn。
2. **老设备零回归**：hello 没有 `codecs` 就当"只会 PCM"；`audioCodec` 默认 `auto`。设备离线时行为与迭代前一致。
3. **决策可解释**：每段回复的档位/依据/切换原因都在 `/api/diag.audio` 里；每段回复只选一次档位。

## 二、编码链路（PCM → Ogg Opus → 裸 Opus 包）

```
TTS 引擎（breeze/edge/sapi）产 24k mono s16le PCM
  → ffmpeg（-f s16le -ar 24000 -ac 1 -i pipe:0
            -c:a libopus -b:a <bps> -application voip -frame_duration 20
            -ar 16000 -f ogg pipe:1）
  → 自写 Ogg page 解析器拆包（跳过 OpusHead/OpusTags）
  → 裸 Opus 包序列（每包 = 一个 20 ms 帧）
  → speech.js 按 20 ms 节奏逐个 WS 二进制帧下发（audio 头 codec=opus → 包… → audio_end）
```

- 新文件：`bridge/lib/opus_encode.js`
  - `OggOpusParser`（增量、可喂任意分块）
  - `encodePcmToOggOpus({pcm,inputRate,bitrate,frameMs,ffmpegPath,timeoutMs,spawnImpl})`
  - `buildFfmpegArgs()`（单测可直接断言参数）
  - 错误码：`OPUS_UNAVAILABLE`（ffmpeg 缺失/ENOENT）、`OPUS_SPAWN_FAILED`、`OPUS_FFMPEG_FAILED`、
    `OPUS_TIMEOUT`、`OPUS_PARSE`、`OPUS_EMPTY`
  - 编码超时 20 s；单包 1..1275 B 强校验。
- ffmpeg 取配置 `ttsFfmpeg`（已有绝对路径）；用 `ffmpegLooksUsable()` 先做**不 spawn** 的存在性检查，
  路径不存在时直接 `OPUS_UNAVAILABLE`，不会每次都白起进程。

### Ogg 解析要点（踩坑清单）

1. **page 结构**：`OggS`(4) + version(1) + flags(1) + granule(8) + serial(4) + seq(4) + crc(4) +
   page_segments(1) + lacing table(n) + payload。CRC 不校验（数据是 ffmpeg 刚生成的管道流），结构错误一律显式报。
2. **lacing = 255 表示包未结束**：一个包可跨多段；某段 <255 才收包。128 kbps 夹具里包长 356..636 B，
   就是 255+余数 两段，单测专门覆盖。
3. **包可以跨 page**：本页最后一段仍是 255 → 下一页 `header_type & 0x01`(continued) 必须置位；
   两页的片段要拼回一个包。解析器对"continued 但没有半包"和"有半包但下一页没 continued"都报错。
   夹具很难自然产生跨页包，单测用手工 Ogg page 构造器覆盖。
4. **头两个包**是 `OpusHead` / `OpusTags`，下行不需要（codec 参数由桥/固件静态约定），跳过；
   顺手校验 magic，出错显式报（第二个不是 OpusTags 时只告警并按音频包处理）。
5. 尾部残缺（半页/半包）在 `finish()` 报错——`ffmpeg` 正常退出不应出现，出现说明流被截断。
6. 包长 1..1275 B 是 RFC 6716 硬约束，越界即数据损坏。

## 三、协议变更（跨线已定，字段名不要改）

### 3.1 设备 hello（可选字段）

```json
{"t":"hello","fw":"hub_v2","board":"watcher","ver":"0.2","cam":1,"w":240,"h":240,
 "codecs":["pcm","opus"],"opusRate":16000}
```

- `codecs`：设备支持的编码；缺省/缺失 = 只会 PCM（老固件）。
- `opusRate`：设备侧 Opus 解码采样率（协商提示；本轮只记录/展示，不下发）。
- 桥侧解析：`protocol.js parseDeviceMessage('hello')` → `msg.codecs/opusRate`；`device.js` 暴露
  `device.codecs`、`device.opusRate`。

### 3.2 下行 audio 头（新增 `codec`）

```json
{"t":"audio","rate":24000,"bits":16,"ch":1,"bytes":0,"seq":7,"codec":"opus"}
```

| 项 | 约定 |
|---|---|
| `codec` | `"pcm"` \| `"opus"`，缺省 `pcm` |
| opus 二进制帧 | **每个 WS 二进制帧 = 一个裸 Opus 包**（20 ms、16 kHz mono、无长度前缀、≤1275 B） |
| opus 头字段 | `rate=24000`（设备解码输出率，不是编码率）、`bits=16`、`ch=1`、`bytes=0`、`seq` 递增 |
| `audio_end` | 语义不变（`seq` 与头一致） |
| PCM | 与迭代前完全一致（`bytes` 为实际 PCM 长度，帧可 >1 个包） |

实现：`protocol.js audioHead()` 增加 `codec` 参数（非法值按 `pcm`）；`contract.js AUDIO` 是这份约定的
机器可读事实源（`AUDIO.codecs/opus.defaultCodec/headRate/adaptive/pongDiag`）。

### 3.3 上行 pong（可选诊断字段）

```json
{"t":"pong","bufMs":120,"underruns":4,"reconnects":2,"rssi":-51,"codec":"opus"}
```

- 全部可选；老设备只有 `{"t":"pong"}`。**缺字段不能报错**，也不能补 0（"没有数据"≠"缓冲见底"）。
- `device.js` 保留 `lastDiag` + 最近 16 条 `pongHistory`；新连接时清空（新会话的健康数据不可信）。

## 四、自适应码率算法与阈值

事实源：`bridge/lib/audio_profile.js`（常量 `ADAPTIVE`，文档/面板/diag 引用同一组值）。

- 窗口：最近 **6 条** pong。
- `bufMs` 取平均；`underruns` 是设备累计计数，取"尾部非递减段"的增量（设备重启计数归零时不会算成巨量欠载）。
- 分类：
  - 健康：平均 `bufMs ≥ 120` 且新增欠载 ≤ 0 → **24 kbps**
  - 中等：平均 `bufMs ≥ 60` 且新增欠载 ≤ 2 → **16 kbps**
  - 差：其它（缓冲低/欠载多/没有健康数据但已失联）→ **8 kbps**
  - 未知：刚连上、还没有 pong → 用配置 `opusBitrate`（默认 16000）
- 关闭自适应（`audioAdaptive=false`）：固定 `opusBitrate`，`tier=fixed`。
- 回退（都在 diag 可解释）：
  - 连续 **2 段** 判"差" → 回退 PCM 24k，并保持 PCM 直到健康度恢复（HOLD，避免来回抖）；
  - 连接后 **60 s** 没有 pong（心跳 25 s/次）→ 判失联 → 回退 PCM；
  - 编码连续失败 **2 次**（或 ffmpeg 不可用）→ 暂停 opus **60 s**（`opusBlockedUntil`），期间 PCM；
  - opus 下发过程中连接断开/被打断 → 本段放弃（丢包不补），补 `audio_end` 收尾。
- **每段回复只选一次档位**：`speaker.speak(text)` 入口调一次 `audio.selectProfile()`，该段所有句子共用
  这个快照；句子中间不切码率（听感 + 设备侧解码路径都稳定）。下一段回复重新评估。

   （测试环境限制，见任务说明）。已用 pwsh 直接调 ffmpeg 确认：`ffmpeg 8.1.1` 带 `libopus`；
   两个夹具就是用与生产完全一致的参数生成的（`-c:a libopus -b:a … -application voip -frame_duration 20 -ar 16000 -f ogg`）。
   生产 DSH 进程内 `spawn` 是否可用，需设备上线后第一次说话验证（失败会显式回退 PCM 并出现在 diag）。

## 八、给固件线的跨线清单（依赖的字段/行为）

- 上行 hello：加 `codecs:["pcm","opus"]`、`opusRate:16000`（可选；不加 = 桥走 PCM）。
- 下行 audio 头：解析 `codec`；`opus` 时把后续**每个 WS 二进制帧**当**一个裸 Opus 包**喂 micro-opus 解码，
  输出 24 kHz mono s16 写 I2S（`rate=24000` 只是头字段，包本身是 16 kHz 带宽编码）。
- `bytes=0` 表示流式（长度未知），`audio_end` 收尾语义不变。
- 上行 pong：建议带 `bufMs`（设备音频环形缓冲剩余毫秒）与 `underruns`（累计欠载次数），
  有 WiFi 就再带 `reconnects/rssi`；`codec` 填当前播放编码。桥按这些字段自适应，缺字段也能跑（按 unknown）。

### 交叉核对（2026-11-03 本轮读到固件线的在改代码）

写文档时只看不改，已确认 `firmware-v2/main` 当前实现与本文一致：

- `proto.cc` BuildHello：`"codecs":["pcm"(,"opus")]` + `"opusRate":16000`（`audio_dec.h` 注释明确
  "桥侧编码采样率；解码器内部 16k→24k 重采样"）——与桥侧"编码 16 k、audio 头 rate=24000"完全对得上。
- `proto.cc` Parse：`audio` 头读 `codec`（未知值整条拒绝），opus 允许 `rate=24000` 或 `16000`（桥发 24000）、
  `bits=16`、`ch=1`；`audio_end` 语义未变。
- `proto.cc` BuildPong：`{"t":"pong","bufMs":…,"underruns":…,"reconnects":…,"rssi":…,"codec":…}`。
- `app_ui.cc` 二进制处理：`s_codec==Opus` 时每帧交给 `audio_dec::PushPacket`（裸包入环，不按 PCM 偶数兜底），
  `audio_end` 时 `audio_dec::Flush()` 收尾；PCM 分支保持原路径。
- 固件对"桥发了 opus 但本机 hello 只报 pcm"有显式 ERROR 日志（本段无声）——桥侧按 hello 协商，
  正常情况下不会触发；若触发，说明桥侧配置被强制 `audioCodec=opus` 且设备能力声明异常。
