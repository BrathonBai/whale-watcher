## 1. 目标与非目标

### 1.1 目标（v1 必须做到）

1. 鲸鲸（SenseCAP Watcher / ESP32-S3）**不再必须连 PC**：手机 dsh-Go 里跑 DSH 引擎，
   设备通过 **BLE** 直连手机 App，App 当「透明网关」把 BLE 消息转给手机里的大脑桥
   （`dsh-embodied-bridge`，DSH 插件）。
2. **协议零改动兼容**：桥的线协议（`bridge/lib/protocol.js` 的 hello/welcome/say/face/
   audio/audio_end/shot/pong/voice/image）保持不变；BLE 只是一条新传输。新增字段全部可选。
3. **音频能在 BLE 带宽下工作**：上下行都用 **IMA ADPCM 4:1**（24 kHz → 约 12 KB/s）；
   WiFi/PC 路径保持原样（PCM / Opus 不变）。
4. **双链路仲裁**：设备同时支持 WiFi-WS（PC 桥）与 BLE（手机桥），同一时刻只有一条生效；
   BLE 连上时 WiFi 侧暂停，BLE 断开自动回退。
5. **dsh-Go 侧不改运行时**：用现成的「guest 插件注入」机制（仿 `AppAuthGuest`）把桥插件
   写进 `/opt/dsh-app/embodied` 并追加 `--patch`，**不需要重建 1GB 运行时**。
6. 设备侧 UI/串口可见状态；手机侧有设置页（开关/扫描/连接/状态/诊断）。

### 1.2 非目标（v1 明确不做）

- **BLE 配对/加密**：v1 链路不加密（见 §8 风险）。LE Secure Connections + 绑定放到 v2。
- 设备侧 Opus **编码**（上行仍 ADPCM；micro-opus 只暴露解码器，编码封装另立任务）。
- 手机原生 TTS/STT 接入桥（v1 用桥现有引擎：Breeze/edge/SAPI；手机端建议 Breeze key 或
  引擎侧 `speechToText` 插件）。v2 再做「App 本地 TTS→桥」。
- BLE OTA、多设备、Mesh、iOS。
- 修改 dsh-Go 的运行时打包（`runtime/build-runtime.sh` / `rtbuild.py`）——用 guest 注入绕过。

## 2. 总体架构

```
                ┌──────────────────────── 手机（Android） ────────────────────────┐
                │                                                                 │
  ESP32-S3      │  dsh-Go App 进程                                                 │
 ┌──────────┐   │  ┌─────────────────────────┐      ┌──────────────────────────┐  │
 │ firmware │   │  │ EmbodiedBleService (FGS)│      │ DSH 引擎（PRoot, app 子进程）│
 │  v2      │◄─BLE─►│  BLE central + 分帧/重组 │◄────►│  dsh web 127.0.0.1:3080+  │  │
 │ link_ble │   │  │  WS client (手写)        │  ws  │  └─ 插件 dsh-embodied-    │  │
 │ adpcm    │   │  └──────────┬──────────────┘      │     bridge  127.0.0.1:7788│  │
 │ link_ws  │   │             │ Method/EventChannel │        (guest 注入)        │  │
 └──────────┘   │  ┌──────────▼──────────────┐      └──────────────────────────┘  │
                │  │ Flutter 设置页「鲸鲸蓝牙」│                                   │
                │  └─────────────────────────┘                                    │
                └─────────────────────────────────────────────────────────────────┘
        WiFi（保留）：设备 ⇄ ws://PC:7788/device ⇄ PC 上的 DSH 桥
```

数据流（BLE 模式）：

```
设备 hello/pong/image/voice  ──BLE帧──► 网关重组 ──WS text/binary──► 桥 device.js
桥 say/face/audio/audio_end/shot ──WS──► 网关分帧 ──BLE帧──► 设备 proto/audio_dec
语音上行：设备 mic 24k PCM → ADPCM(12KB/s) → voice 头 + 二进制块 → 桥解码→WAV→ASR
语音下行：桥 TTS 24k PCM → ADPCM(12KB/s) → audio 头(codec=adpcm)+块 → 设备解码→I2S
```

关键点：**网关不解释业务负载**（只做分帧/重组/透传），编解码协商全在桥与固件之间。

## 3. BLE GATT 规格

| 项 | 值 |
|---|---|
| 角色 | 设备 = GATT peripheral（广播）；Android = GATT central |
| 设备名 | `Jingjing-XXXX`（XXXX = BLE MAC 末两字节大写 hex；便于人眼识别） |
| Service UUID | `6a696e67-6a69-6e67-8000-000000000001` |
| Char DOWN（手机→设备） | `6a696e67-6a69-6e67-8000-000000000002`，properties = **Write Without Response** + Write |
| Char UP（设备→手机） | `6a696e67-6a69-6e67-8000-000000000003`，properties = **Notify** |
| CCCD | UP 上标准 0x2902，写 `0x0001` 开启通知 |
| 广播 | 128-bit Service UUID + flags；scan response 带设备名；interval 100 ms（常开） |
| MTU | 设备 preferred 247；Android `requestMtu(247)`；协商后 `payload = MTU - 3`（ATT 头） |
| 连接参数 | 设备请求 interval 12–24 ms、latency 0、timeout 4 s（Android 通常给 15 ms） |
| PHY | 尝试请求 2M（失败不报错） |
| 安全 | v1 **无加密、无绑定**（见 §8） |

> DOWN 用 Write Without Response 是为了吞吐；设备侧必须处理「写太快」——见 §5.4。
> UP 每帧一条 notification（≤ MTU-3）。

## 4. BLE 分帧（transport framing）

一条逻辑消息（= 一条 WS text 或 binary 消息）被切成若干 BLE 包。**每个 BLE 包 = 7 字节头 + 负载**。

```
偏移  长度  字段
0     1     magic  = 0xA5
1     1     type   = 0x01 text(JSON 控制消息) | 0x02 binary(音频/图片数据)
                      0x10–0x1F 保留给传输层控制帧（v1 不用，收到即丢并计数）
2     1     flags  bit0 = FIRST, bit1 = LAST，其余保留 0
3     1     frag_index（0 基）
4     1     frag_total（≥1）
5     2     payload_len（LE uint16，本包负载字节数）
7     N     payload（N = payload_len ≤ MTU-3-7）
```

- 单包消息：`frag_index=0, frag_total=1, flags=FIRST|LAST`。
- 消息上限：**text 4096 B / binary 16384 B**（与桥 `MAX_FRAME_BYTES`、固件
  `kMaxBinaryPayload` 对齐）。`frag_total` 用 uint8，MTU=247 时 binary 最大 70 片，够用。
- 接收方按 `frag_index` 严格顺序重组；出现不连续、`frag_total` 超限、`payload_len` 超限、
  magic 不符 → **丢弃该消息并计数**（不重传，v1 不做 NACK）。超时 3 s 未收全的消息丢弃
  （每连接最多 2 个进行中的消息：1 个 text + 1 个 binary）。
- 类型不认识的包（例如未来控制帧）静默丢弃并 `rxDrop++`，不能断链。
- 文本消息按 UTF-8 原样传，网关不解析。

### 4.1 为什么不做应用层 ACK

BLE 链路层自带重传（LL ACK），NimBLE 的 `notify` 在 mbuf 不足时返回错误——设备侧据此
**重试而不是丢帧**（背压）；Android 侧 notify 回调顺序可靠。v1 用「可靠的 BLE + 设备侧
重试 + 计数器」覆盖；真正的应用层 ACK/NACK 留到出现实测丢包后再加（协议预留了类型段）。

## 5. 设备侧传输层（firmware-v2）

### 5.1 模块划分（2026-11-13 v0.4：BLE-only）

2026-11-13 晚用户确认：**设备固件取消 WiFi / PC 桥，只保留 BLE**（手机、以后 PC 都作为 BLE
central 连设备）。v0.4 已删除 `net_wifi.*` / `ws_client.*` / `ws_frame.*` / `bridge_find.*` /
`nvs_creds.*` / `wifi_local.h`，`main/CMakeLists.txt` 不再依赖 `esp_wifi` / `esp_netif` /
`esp_http_client`；`link` 只剩 BLE 一条链路。

| 文件 | 职责 |
|---|---|
| `link.h` / `link.cc` | **BLE-only 传输门面**：`Init/Start` 只起 NimBLE；监控任务维护 `Active()`/重连计数；首次 NimBLE 初始化失败每 3 s 重试 |
| `link_ble.cc` | NimBLE GATT server、广播、连接管理、分帧/重组、TX 队列 + TX 任务、RX 任务 |
| `adpcm.h` / `adpcm.cc` | IMA ADPCM 编/解码（无 esp 依赖，可被主机测试） |
| `console.cc` | 极简 UART0 行命令：`>help` / `>link` / `>link reconnect` / `>stat` / `>adpcm`（**不再有** `auto/ble/wifi`） |
| `proto.*` | hello 字段、`voice.codec/samples`、`audio.codec=adpcm`、pong 传输字段；固件版本 `0.4` |
| `app_ui.cc` | 所有 `ws::` → `link::`；mic 上行按 `link::UplinkCodec()` 编 ADPCM；hello 重发；**配网向导改为蓝牙配对**（见下） |
| `app_main.cc` | `link::Init()` / `link::Start()`；不再有 WiFi 凭据 / 桥地址 / 模式恢复 |

`link::` API（上层只看这个）：

```cpp
namespace link {
enum class Kind : uint8_t { None = 0, Ble };

struct Stats {            // 汇总，pong 与串口都用它
  Kind active; bool ble_connected;
  int reconnects; int tx_frames; int rx_frames;
  int tx_drop; int rx_drop; int mtu; int rssi;
  char name[24];
};
void Init();                       // 建 RX 分发/监控任务；NVS 需已 init
void Start();                      // 初始化 NimBLE 并开始广播（失败自动重试）
Kind Active();                     // None=未连接 / Ble=已连接
bool Connected();                  // Active() != None
const char* UplinkCodec();         // "adpcm"（已连接）/ "pcm"（未连接）
bool SendText(const char*, size_t);
bool SendBinary(const uint8_t*, size_t);
void SetTextHandler(void (*)(const char*, size_t));
void SetBinaryHandler(void (*)(const uint8_t*, size_t));
void SetOnSubscribed(void (*)());  // 手机打开 UP 的 CCCD 时回调（app_ui 立刻补发 hello）
Stats Get();
const char* KindName(Kind);
int TxQueuedBytes(); void Reconnect();
}
```

语义要求：

- 回调**在 BLE RX 任务上下文**调用（不要在 NimBLE host task 里解析 JSON），与旧 `ws::`
  回调上下文语义一致（短小、只入队）。`SetOnSubscribed` 例外：它在 NimBLE host task 里执行，
  回调只允许置标志/入队。
- `SendText/SendBinary` 立即返回是否**入队**成功；绝不阻塞 UI 任务。TX 队列 = 32 KB
  环形缓冲（PSRAM），满时：text 丢弃并 `tx_drop++`；binary 丢最旧的并 `tx_drop++`。
- **没有 Mode / NVS 模式 / 桥地址**：`Start()` 直接起广播；WiFi 相关 API、`wifi_local.h`、
  `>link auto|ble|wifi` 全部删除；`>link reconnect` = 断开当前连接并恢复广播。
- **蓝牙配对向导**（取代原 WiFi 配网）：开机第一屏显示
  `蓝牙配对: 打开手机 App 的鲸鲸蓝牙` + `本机名 Jingjing-ACB2`；长按菜单第二项由「配网」
  改为「蓝牙」，进入后显示同样提示（已连接则显示 `蓝牙已连接 mtu N`）；链路断开时显示
  `蓝牙已断开 / 重新打开手机 App 的鲸鲸蓝牙`。
- 启动顺序（真机教训）：`app_ui::Init()`（音频流/解码任务/触摸/LED）与 UI 任务栈必须在
  `link::Init()` 之前；没有 TF 卡时不要调 `mp3::Init()`——它会在内部 RAM 申请 ~24 KB，
  把 BLE 运行期内部堆压到 10 KB 级，拍照（SSCMA SPI 队列）随即失败。
- 内存（2026-11-13 v0.4 真机）：`[mem] after-app 内部 free=119,215 largest=47,104 |
  PSRAM free=6,673,160`（对比 BLE 第一版 WiFi+BLE 时代的 34.7 KB，主要是 WiFi 协议栈/缓冲
  不再链接与初始化；bin 也从 6.95 MB 降到 6.51 MB）。
- 每次 `Active()` 从 None→Ble 或 Ble→None，都算一次「新连接」：`app_ui` 据此重发 hello。

### 5.3 TX 路径

`SendText/SendBinary` → 拷进 TX 环形缓冲（带 msg 描述）→ 唤醒 `bletx` 任务（优先级 6，
栈 4096）→ 按当前 MTU 切片 → 逐包 `ble_gatts_notify_custom`：

- 返回 `BLE_HS_ENOMEM`/忙 → `vTaskDelay(pdMS_TO_TICKS(2))` 重试（同一片最多 200 ms，
  超时算 `tx_drop += 剩余字节` 并丢弃整条消息，`ESP_LOGW` 限频）。
- 每发 4 片让出 1 ms，避免饿死同优先级任务。
- `Active()!=Ble` 时入队直接失败返回 false（与旧 `ws::SendText` 未连接语义一致）。

### 5.4 RX 路径

NimBLE GATT write 回调（host task）只做：校验 7 字节头 → 拷进重组缓冲 → 完整消息入
`rxq`（2 个槽位、带 kind）→ 通知 `blerx` 任务（优先级 6，栈 6144）调用上层回调。
重组缓冲：text 用内部 RAM 4 KB；binary 用 PSRAM 16 KB。

## 6. 音频编码：IMA ADPCM（上下行）

### 6.1 参数

| 项 | 值 |
|---|---|
| 算法 | IMA/DVI ADPCM，4 bit/sample，标准 step/index 表（**与 ffmpeg `adpcm_ima_wav` 同构**） |
| 采样率 | 24000 Hz（与现有 mic/播放环一致，**不做重采样**） |
| 声道/位宽 | mono / 源 PCM 16 bit |
| 码率 | **12041 B/s**（1024 B / 2041 采样 × 24000） |
| 整块 | **1024 字节 = 4 B 头 + 1020 B nibbles = 2041 采样 = 85.04 ms** |
| 块头 | `[0..1] predictor(int16 LE) = 本块第一个 PCM 采样`、`[2] index(uint8)`、`[3] reserved=0`、`[4..1023] nibbles`（**低半字节在前**） |
| 末块 | 短块 = 4 B 头 + `ceil((n-1)/2)` B，n（本块采样数）必须为**奇数**；编码器遇到偶数会补 1 个采样，解码端用 `samples` 字段裁掉 |

**块头带 predictor/index** 的原因：BLE 丢一帧不会让后续整段变噪；接收端从块头恢复状态即可
（每块独立可解，最多丢 85 ms）。

### 6.2 编码/解码等价性与参考实现

- C（`firmware-v2/main/adpcm.cc`）与 JS（`bridge/lib/adpcm.js`）必须**逐字节一致**：
  step 表、index 表、`diffq`、predictor 钳位 `[-32768,32767]`、index 钳位 `[0,88]`、
  「先按旧 index 的 step 更新 predictor 再调 index」的顺序都与 ffmpeg 相同。
- **已用 ffmpeg 交叉验证**（2026-11-13）：`bridge/lib/adpcm.js` 解码 ffmpeg 产出的
  `adpcm_ima_wav` 流，与 ffmpeg 解码结果 **逐采样 0 差异**；JS 编码的流交给 ffmpeg 解码，
  与 JS 解码 **逐采样 0 差异**（证据与向量见 `bridge/test/fixtures/adpcm-vectors.json`
  的 note 字段；生成环境 ffmpeg 8.1.1）。
- 共享测试向量：`bridge/test/fixtures/adpcm-vectors.json`
  - `decode[]`：ffmpeg 编码的块 + ffmpeg 解码 PCM（验证解码器）；
  - `encode[]`：PCM + JS 编码字节（验证 C/JS 编码一致；含一个 113 采样短块）。
  C 侧自检命令 `>adpcm` 逐条比对并打印 `PASS/FAIL`；桥单测必须全绿。
- `samples` 字段（新增、可选但推荐）：`voice`/`audio` 头里的 `samples` = 解码后应有的
  PCM 采样数；末块补齐的 1 个采样靠它裁掉。设备/桥都在有值时严格遵守、无值时不裁。

### 6.3 线上位置

- **上行**：`{"t":"voice","bytes":N,"samples":S,"seq":S2,"rate":24000,"bits":16,"ch":1,"codec":"adpcm"}` +
  N 字节 ADPCM（可任意切成 ≤16384 的二进制帧，接收端按块 stride 解码）。
  `bytes` = ADPCM 字节数（含块头）；`samples` = 解码后 PCM 采样数。10 s ≈ 120,000 B
  （旧 PCM 是 480,000 B）。
- **下行**：`{"t":"audio","codec":"adpcm","rate":24000,"bits":16,"ch":1,"samples":S,...}` +
  ADPCM 二进制块 + `{"t":"audio_end"}`。设备 `audio_dec` 按 `codec` 选路径，ADPCM 解码 →
  24k PCM 环形缓冲（有 `samples` 时按它裁剪；短块在 `audio_end` 时 flush）。
- 老组合（WiFi/PC）不变：`codec` 缺省 = `pcm`；Opus 路径不动。

| 字段 | 值 | 说明 |
|---|---|---|
| `transport` | `"ble"` / `"wifi"` | 当前生效链路 |
| `uplink` | `"adpcm"` / `"pcm"` | 本会话 voice 二进制用的编码 |
| `mtu` | int | BLE MTU（wifi 时 0/省略） |
| `name` | string | 显示名（`Jingjing-XXXX`） |

`hello.codecs`（既有字段）语义扩展为「设备能解码的下行编码」：BLE 固件报
`["pcm","opus","adpcm"]`；`opus` 仍只在解码器可用时报。

`hello.ver` 从 `"0.2"` 升到 **`"0.3"`**（BLE/ADPCM 固件）。`hello` 的时序（真机补充）：
BLE 连接建立瞬间设备就先发一帧 hello（此时 MTU 仍是 23、手机通常还没订阅通知，会丢）；
手机把 UP 的 CCCD 打开后，设备会**立刻补发一次 hello**（`ver`/`mtu`/`transport` 都是最新值）。
桥不需要特殊处理，但可以在订阅后把「等 hello」的超时从 10 s 降到 ~1 s。

`pong` 新增（诊断，桥只展示）：`transport`、`mtu`、`txDrop`、`rxDrop`；`rssi` 在 BLE 时
填 BLE RSSI（桥的 `audio_profile` 只把它当展示值）。

`voice` / `audio` 新增 `codec` 字段，规则见 §6.3；两者都可带可选 `samples`（解码后采样数）。

`welcome`/`say`/`face`/`shot`/`audio_end`/`image`/`result` **完全不改**。

桥侧校验（`bridge/lib/protocol.js`）：
- `hello.transport` ∈ {ble,wifi}（缺省按 wifi），`hello.uplink` ∈ {pcm,adpcm}（缺省 pcm）；
- `voice.codec` ∈ {pcm,adpcm}，缺省 pcm；`voice.bytes` 上限：pcm 576000、**adpcm 240000**；
  `voice.samples` 可选，1..480000；
- `audio.codec` ∈ {pcm,opus,adpcm}，缺省 pcm；`audio.samples` 可选。

## 8. 安全与已知风险（v1 明示）

1. **BLE 链路不加密**：附近设备可连接并冒充手机。缓解：设备侧广播名带后缀、v2 加 LE SC
   绑定 + 配对窗口。**这是 v1 已知限制，不是 bug**。
2. **桥监听 127.0.0.1 但仍可被本机任意 App 访问**：手机 App 沙箱内所有应用共享 loopback。
   v1 给桥加 `wsToken`：guest 注入的 patch 里写入随机 token，网关联 URL `?token=`；
   桥在 `wsToken` 非空时校验 query token，错误返回 401。PC 默认 token 为空 → 行为不变。
3. 桥 `discover`（UDP 7789）在手机无意义：新增 `discover:false` 配置，guest patch 关掉。
4. 手机后台被杀 → BLE 断：靠前台服务 + App 的省电白名单引导页（复用现有
   `background_guide_page`）。v1 不自建保活。
5. 桥 `dataDir` 在 `/root/.dsh/plugins-data/embodied-bridge`，音频/图片落盘会占手机空间：
   沿用桥的 `imageKeep/voiceKeep`，patch 里降到图片 5 张 / 语音 20 段。
