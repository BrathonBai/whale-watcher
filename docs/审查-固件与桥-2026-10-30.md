## 2. P0：`nvs_flash_init()` 从来没调用过

**症状**（修之前）：

- 串口 `>wifi TT-W8BQ 12345678` → `保存失败（NVS 写入出错）`
- `>status` → `wifi: 未连 ssid="" 来源=本机 wifi_local.h`
- 日志里每秒 `wifi: 断开 (reason 201)`（201 = NO_AP_FOUND，还在找旧网络）

**根因**：`main/app_main.cc` 从头到尾没有 `nvs_flash_init()`（整个工程只在
`wifi_setup.cc` 的 `SaveWithFallback()` 里调过一次，作为"擦库重试"的兜底）。后果是三重的：

1. `net::WifiStart()` 里 `nvs_open("wifi", NVS_READONLY)` 必然失败 → ① 应用 NVS 那条路永远走不通；
2. `esp_wifi_init` 也读不到 `nvs.net80211` → ② 驱动 NVS 那条路同样失效；
3. `net::SaveCredentials()` 写不进去 → 串口 `>wifi` 永远报保存失败。

于是唯一还能用的凭据来源只剩 ③ 编译期 `wifi_local.h`。**换网络＝只能重刷固件**，这就是这次离线的真因。

这也解释了为什么"配网向导"看起来能用：它的 `SaveWithFallback()` 在失败后会
`nvs_flash_erase(); nvs_flash_init();` 再写一次 —— 也就是说**向导是在绕过这个 bug**，
而串口那条路没有兜底，直接暴露。两条路一条是 workaround、一条是裸奔。

**修复**（`main/app_main.cc`，`net::WifiStart()` 之前）：

```cpp
#include "nvs_flash.h"
...
    esp_err_t nvs = nvs_flash_init();
    if (nvs == ESP_ERR_NVS_NO_FREE_PAGES || nvs == ESP_ERR_NVS_NEW_VERSION_FOUND) {
        ESP_LOGW(TAG, "NVS 需要重建（%s），擦除后重试", esp_err_to_name(nvs));
        nvs_flash_erase();
        nvs = nvs_flash_init();
    }
    ESP_LOGI(TAG, "NVS %s", nvs == ESP_OK ? "就绪" : "初始化失败（配网写入会失败）");
```

**验证**（修之后，同一条命令）：

```
W (77463) wifi: 已保存 WiFi 凭据 ssid="TT-W8BQ"（成功），重启生效
已保存 ssid="TT-W8BQ"，2 秒后重启
...RTC_SW_CPU_RST → 重启
>status: wifi 已连 ssid="TT-W8BQ" ip=192.168.66.14 来源=应用 NVS(wifi/ssid)
```

`来源` 从 `本机 wifi_local.h` 变成 `应用 NVS(wifi/ssid)`，就是修复生效的判据。

**怎么刷的**（照 `build.ps1` 的约定，只动 ota_1，ota_0 留作退路）：

```powershell
$env:IDF_TOOLS_PATH='C:\Espressif'; $env:IDF_PATH='C:\Espressif\v5.5\esp-idf'
. 'C:\Espressif\v5.5\esp-idf\export.ps1'
cd "$env:LOCALAPPDATA\hubdev\device"; idf.py build      # 需先清 build（见 §5 CMake 报错）
& 'C:\Espressif\python_env\idf5.5_py3.11_env\Scripts\python.exe' -m esptool `
  --chip esp32s3 -p COM6 -b 921600 --before default_reset --after hard_reset `
  write_flash 0xe00000 build\hub_device.bin
```

体积：`0xa40050` B / 分区 `0xc00000`（余 15%）。

## 3. 固件侧其它"写了没接上"的东西

| # | 现象 | 判定 | 处理 |
|---|---|---|---|
| 1 | `proto::BuildPress()` 从未被调用 | `SendPress()` 用 `snprintf` 内联发 `{"t":"press","edge":..,"count":..}`，能发；`BuildPress` 是死代码（而且它签名里没有 `count`，当初就是因为带不了双击才内联的） | 保留，标注为 dead；要么删，要么把 `count` 加进签名统一走它 |
| 2 | `proto::BuildLevel()` 从未被调用 | 设备**根本不发 `level`**（触摸压力）。固件注释与 `proto.h` 把它写成契约的一部分，桥里也老老实实解析 —— 这是典型的"纸面能力" | 桥侧解析保留（向前兼容），文档里删掉"触摸压力上行"的暗示；要用就真在 `input.cc` 里发 |
| 3 | `s_welcomed` 只写不读 | 收 `welcome` 时置 true，断线时置 false，没有任何分支读它 | 无害，可删 |
| 4 | 串口命令表帮助里漏了 `>wifi` / `>mic` / `>auto` / `>keys` 等 | 只有出错时才打印一行命令表，且不全 | 补全帮助文本 |
| 5 | 30s 未联网自动开菜单 | 行为是对的，但菜单会盖住脸 8 秒；期间桥发来的 `face` 只改底层 mood，看不见 | 可接受；知道就好 |

契约核对（双向都过了一遍）：

- 下行 `welcome/say/face/audio/audio_end/record/mic/ping/result` —— `proto::Parse` **九种全认**，
  `ApplyDownlink` **九种全处理**（`record` → `voice::Trigger(seconds)`，`mic` → `voice::SetAuto`）。
- 上行 `hello/press/text/state/sound/voice/diag/pong` —— 固件都真的发（`BuildPress/BuildLevel` 除外）。
- 录音时长：固件 `kMaxSec = 10`，桥侧 `recordMaxSeconds = 10`，一致；`voice::Trigger(seconds>0)`
  确实按秒数收尾（不是"猜静音"）。

## 5. 环境侧踩到并记下来的坑

- **CMake 报 `File can't be removed and still exist: esp-idf\esp_hw_support\libesp_hw_support.a`**
  → 不是代码问题，是 build 目录状态坏了（上一轮 configure 中途失败留下半成品）。
  直接删 `build/` 全量重建即可（本次 1127 个目标，约 4 分钟）。
- **串口 RX**：一开始发 `>wifi` 没反应，以为是 RX 没接。真相是**命令到了、写入失败**（就是 §2 的 bug）。
  判别方法：随便发一行不带 `>` 的文本，固件会回 `看不懂（命令要以 > 开头）` —— 有回显就说明 RX 是通的，
  没有才是硬件问题。
- **esptool 能自动复位**：`--before default_reset` 有效（CH342 的 DTR/RTS 接了）。手写 DTR/RTS 时序
  反而复不了位，别折腾。
- **`wifi_local.h` 是生成物**：由 `build.ps1` 从 `%LOCALAPPDATA%\hubdev\wifi.env` 生成到构建副本，
  仓库里没有。本次已把它更新成 `TT-W8BQ / 12345678 / ws://192.168.66.161:7788/device`。

## 7. 复跑中观察到的三件事

1. **TTS 流式头 `bytes=0` 是合法的**。桥的 breeze 流式路径先发 `{"t":"audio","bytes":0}` 再推 PCM，
   看起来像"总长度缺失"。查了固件 `audio::Begin()`：同一 `seq` 重复 head 会累加 `s_expect_bytes`，
   而 `Push()` 只受环形缓冲 `kRingBytes` 约束、不看期望值 —— 所以 0 是"长度未知"的约定用法，
   播放不受影响。**结论：不是 bug，别去"修"。**
2. **旋钮是音量，不是菜单**。现场转了一下，串口打出 `旋钮转动（顺） 音量 80% → 100%`。
   这是固件本地行为，协议里没有对应消息，桥侧也就无从控制 —— 想让它可控得加一条下行。
3. **观察到一次 1.5 秒自愈重连**（`05:48:17 设备断开` → `05:48:19 已连接`）。
   当时正在推 86 KB breeze 流式音频（≈24 kB/s，比实时还慢），所以不是"灌爆"。
   重连后 uptime 连续（没重启），且发生在人正在操作设备的时候。**未复现，先记录**；
   两侧的重连逻辑都在（固件 `ws_client` 退避重试 + 桥 `onClose` 清理），所以是自愈的。

## 8. 还没解决 / 需要你知道


- 设备当前连的是**在跑的 v0.1 插件实例**（`device_status` 报在线）。桥 v0.2 要**重启 DSH** 才生效；
  重启后设备会重连，工具会多出 `device_events` / `device_mic`。
- `建图/地图` 之类"写在文档里"的能力没有对应固件：`level`(触摸压力) 是空白，别在演示里提。
- 配网向导（30s 自动弹菜单 → 选中 → AP `Watcher-XXXX` → `192.168.4.1`）**是可用的**，
  但它依赖 `SaveWithFallback` 的擦库兜底；现在串口 `>wifi` 也能用了，两条路都在。
